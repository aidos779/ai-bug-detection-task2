## Информация о проекте

Название работы: AI Tools for Software Bug Detection A Reproducible Pilot Benchmark.

Авторы: Baltabay Aidos и Bissen Yerkebulan. Формат работы: в паре.

Публичный репозиторий: [https://github.com/aidos779/ai-bug-detection-task2](https://github.com/aidos779/ai-bug-detection-task2)

Исследование продолжает RQ2 из Task 1 о сравнительной эффективности AI-инструментов обнаружения ошибок. Для исполняемого пилота область сужена до Python и двух семейств дефектов: деление на ноль и непреднамеренное разделение состояния через изменяемые аргументы по умолчанию.

## Тип исследования и исследовательский вопрос

Тип: количественное сравнительное исследование. Для двух методов измеряются предсказания на одних и тех же размеченных фрагментах кода, качество классификации и вычислительные затраты. Обзор литературы из Task 1 задаёт контекст и ограничения интерпретации.

RQ: повышает ли обучаемый лексический классификатор F1 обнаружения указанных дефектов относительно фиксированных правил AST на одинаковой тестовой выборке из отдельных проектов при соблюдении порогов ложных тревог и ресурсов?

## Гипотезы и критерий результата

Обозначим ΔF1 = F1(NB) - F1(Static). F1 относится к популяции фрагментов в зарегистрированной области и при заданном составе классов, а не ко всем программным ошибкам.

H0: ΔF1 ≤ 0. Обучаемый классификатор не улучшает F1 относительно статического baseline. H1: ΔF1 > 0. Обучаемый классификатор улучшает F1 в тех же условиях.

Положительная нижняя граница парного 95% bootstrap-интервала служит свидетельством в пользу H1 в пределах пилота. Практический успех дополнительно требует наблюдаемого прироста F1 не менее 0,05 и выполнения всех guardrails. Интервал, включающий ноль, не устанавливает превосходство и не доказывает эквивалентность.

## Контрольная группа и AI метод

Baseline: фиксированный анализатор AST. Он отмечает литерал нуля справа от /, // или %, а также литералы list, dict и set в значениях аргументов по умолчанию. Правила не меняются после просмотра тестовых результатов.

AI метод: multinomial Naive Bayes по частотам лексических токенов кода. Словарь и априорные вероятности строятся только на train; alpha = 1,0, порог = 0,5. Это небольшой обучаемый классификатор; результаты ограничены этим методом и двумя семействами дефектов.

## Матрица переменных

| Тип | Переменные и условия |
| --- | --- |
| Независимая | Метод детекции: Static AST Rules или Multinomial NB. Оба метода получают один и тот же исходный текст. |
| Зависимые | F1, precision, recall, FPR, TP/FP/TN/FN; p50 и p95 задержки в мс; throughput в фрагментах/с; peak RSS общего процесса в MiB; время обучения в мс. |
| Контролируемые | Те же train/test и метки; состав классов; извлечение контекста; отсутствие пересечения проектов; Python 3.12.10 и фиксированный Docker digest; один host и архитектура; один процесс, 1 CPU; alpha 1,0 и порог 0,5; seed 42; 5 прогревов и 30 повторов. |
| Фактор стратификации | Семейство дефекта: division_by_zero или mutable_default. Анализ по категориям является вторичным, а не рандомизированным воздействием. |

## Метрики и их назначение

| Роль | Показатель и правило |
| --- | --- |
| Primary | F1 = 2TP / (2TP + FP + FN); основная статистика ΔF1 между методами. Практический порог прироста: 0,05 абсолютной доли, то есть 5 процентных пунктов. |
| Secondary | Precision = TP / (TP + FP); Recall = TP / (TP + FN). Публикуются confusion matrix, показатели по категориям, p50/p95, throughput и время обучения. |
| Guardrail качества | FPR = FP / (FP + TN) ≤ 0,10 для каждого метода. Отдельное ограничение не даёт скрыть ложные тревоги за высоким recall. |
| Guardrail задержки | p95 отдельного вызова детектора ≤ 100 мс для каждого метода после прогрева. Загрузка данных и обучение не входят в эту задержку. |
| Guardrail памяти | Peak RSS общего процесса ≤ 256 MiB. Docker запускается с лимитом 512 MiB. RSS включает обучение и анализ и не сравнивает память моделей по отдельности. |
| Guardrail надёжности | Ноль ошибок измерения. Невалидная конфигурация, синтаксис, метки или пересечение split завершают запуск с ненулевым кодом. |

Если знаменатель precision, recall или F1 равен нулю, инструмент записывает 0. FPR без отрицательных примеров не определена: записывается null, guardrail не пройден. Задержки измеряются perf_counter_ns, throughput считается по суммарному времени вызовов детектора.

## Тестовые данные и честный baseline

Сэмпл W6: отдельные train.jsonl и test.jsonl по 8 строк. В каждом файле 4 положительных и 4 отрицательных примера. Это вручную созданные синтетические фикстуры. Статические правила ожидаемо дают F1 = 1,00, NB = 0,80; ΔF1 = -0,20. Их назначение - проверка исполнения и расчётов, без проверки исследовательских гипотез.

Ограничения baseline: нет анализа достижимости, значений переменных, намеренно общего состояния и межпроцедурного потока. Сравнение относится к этим явным правилам; оно не устанавливает превосходство над промышленными анализаторами.

## Протокол основного пилота на Неделе 7

1. Собрать минимум 50 train-фрагментов и 100 test-фрагментов из минимум 10 отдельных тестовых проектов. Целевой состав: train 25/25, test 50/50 по положительным и отрицательным меткам; в test по 25 положительных и отрицательных на каждое семейство. Этот case-control состав не оценивает распространённость ошибок в эксплуатации.

2. Оба автора независимо размечают примеры по исходному контексту, bug-fix commit и/или регрессионному тесту; разногласия разрешаются до заморозки test. Изменяемый default считается дефектом только при непреднамеренном общем состоянии. Сохраняются provenance и label_rationale, включая основания для отрицательных меток.

3. Разделить данные по целым проектам. Удалить совпадающие AST и вручную проверить переименованные и близкие клоны. Дефектная функция и её исправление остаются в одном split. Удалить подсказки метки из комментариев и метаданных. Зафиксировать SHA-256 данных и конфигурации; test не используется для выбора порога или alpha.

4. На одном host выполнить обучение NB, 5 прогревов и 30 повторов обоих детекторов. Seed 42 определяет порядок примеров и методов. Запуск сохраняет summary.json, predictions.csv и latencies.csv; время обучения публикуется отдельно.

5. Рассчитать ΔF1 и парный 95% percentile bootstrap-интервал: 10 000 повторных выборок целых проектов, одинаковых для обоих методов. Выборки без одного из классов исключаются; число допустимых повторов публикуется. Такой интервал в небольшом пилоте носит исследовательский характер. Отдельно проверить практический порог, guardrails и результаты по категориям.

## Угрозы валидности и меры контроля

Внутренняя валидность: утечки между split, ошибки разметки и настройка на test. Контроль: разделение проектов, проверка клонов, независимая разметка и заранее фиксированная конфигурация. Метрики на test не используются для ретроспективного изменения условий.

Внешняя валидность: две категории, Python, небольшой case-control набор и ограниченный baseline не представляют все AI-инструменты и реальные пропорции дефектов. Выводы сохраняют эти границы. Для переноса нужны отдельные проекты, другие семейства и измерение при естественном составе классов.

Ресурсные измерения: частоты CPU, нагрузка host и общий RSS влияют на результаты. Контроль: одинаковый host, образ, 1 CPU, прогрев и случайный порядок вызовов. Побитовая повторяемость времени и отдельная память каждой модели не заявляются.
